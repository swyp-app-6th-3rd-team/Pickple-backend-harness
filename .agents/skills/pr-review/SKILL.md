# PR Review

작업 중인 저장소의 `AGENTS.md`와 실제 변경 사항을 기준으로 리뷰한다. 스타일 선호보다 사용자 동작에 영향을 주는 문제를 우선한다.

## 검토 대상을 고정한다

- 기존 PR은 현재 base/head와 커밋, 변경 파일, 리뷰 대화를 확인한다. 연결된 GitHub 도구를 우선 사용하고 부족한 기능은 인증된 `gh`로 확인한다.
- 로컬 자체 리뷰는 요청한 기준 브랜치와 커밋 범위를 확인한다. PR 전 리뷰라면 기준과의 커밋 diff뿐 아니라 staged·unstaged·untracked 변경도 범위에 포함했는지 밝힌다.
- 기준을 `develop`으로 고정하지 않는다. 하네스 저장소와 백엔드의 기본 브랜치는 다를 수 있다. 원격을 새로 확인하지 못했으면 로컬 참조 기준이라고 적는다.
- diff 주변의 실제 호출자·보안 필터·SQL·테스트를 좁게 읽는다. 기존 코드와 테스트가 배제한 상황을 새 버그로 주장하지 않는다.
- 변경 파일 중 인증·인가, 데이터 갱신·마이그레이션, 외부 부작용 경로부터 읽는다. 참조 탐색 도구가 있으면 활용하고, 없어도 심볼 검색과 호출 경로 확인으로 리뷰를 계속한다.

## 변경에 해당하는 항목만 확인한다

| 변경 | 확인할 근거 |
| --- | --- |
| API·인증 | SPEC와 요청/응답 호환성, 게스트 정책, 다른 사용자의 리소스 접근, SecurityConfig·OpenAPI·PUBLIC_ENDPOINTS의 일치 |
| 데이터·쿼리 | 트랜잭션 경계, 중복 처리·동시성, 조회 횟수, 정렬·페이지 경계, 인덱스와 데이터 정합성. 저장소의 `throw new XxxException`이 정책 판단인지 인프라 실패인지, 도메인 검증 예외의 단순 전파인지 구분하고, 무결성 오류의 원인 보존·rollback-only 이후 정상 반환·`INSERT IGNORE`에 의한 오류 은폐를 확인한다. |
| Flyway | 버전 중복, 이미 적용된 파일 수정, 빈 DB와 기존 스키마의 업그레이드 경로 |
| 외부 연동 | timeout·실패·부분 성공 처리, 재시도 시 중복 부작용, 테스트와 운영 설정의 차이 |
| 오류 처리·로그 | 예외가 올바른 HTTP 상태·오류 계약으로 변환되는지, 실패 시 롤백·보상이 계약에 맞는지, 응답·로그에 내부 정보나 비밀값이 노출되는지, 운영 진단에 필요한 로그와 수준이 적절한지 |
| 구조·하네스 | 실제 패키지 규칙, 스킬 실행 조건·참조 경로·도구 가용성, 기존 규칙과의 충돌, 설정에 비밀값 포함 여부 |

성능 문제는 쿼리·호출 경로나 측정 근거로 뒷받침한다. 재현 검증이 필요하면 변경에 가까운 로컬 테스트를 실행한다. 라이브 상태를 바꾸는 실험은 같은 작업에서 명시적으로 허용된 범위에서만 수행하고, 허용 여부가 불명확하면 독립적인 리뷰를 먼저 마친 뒤 필요한 권한을 요청한다.

보안 관련 변경은 외부 입력 → 인증 주체 → 소유권 검사 → 저장·외부 호출의 신뢰 경계를 따라 확인한다. 발견한 비밀값은 파일·위치만 보고하고 안전한 저장소로 이전 및 필요 시 폐기·교체를 제안한다. 자격 증명 교체나 운영 설정 변경은 리뷰의 자동 후속 작업이 아니다.

## 결과

- 발견 사항마다 중요도, 정확한 파일·줄, 발생 조건, 사용자 영향, 수정 방향을 적는다. 추정만 남은 내용은 확정된 결함과 분리한다.
- 중요도는 실제 영향과 발생·악용 조건으로 정한다. 취향 수준 제안은 동작 결함과 구분하며, 완료를 막는 결함처럼 취급하지 않는다.
- 문제가 없으면 그 사실과 검토 범위를 간단히 밝힌다. 빈 리뷰를 채우기 위해 사소한 지적을 만들지 않는다.
- 실행한 테스트, 실행하지 못한 검증, 확인한 CI의 커밋·결과를 구분한다. 로컬 통과를 원격 CI·배포 성공으로 표현하지 않는다.
- 리뷰만 요청받았다면 결과를 현재 대화에 보고한다. 같은 작업에서 이미 허용된 PR 작성 범위는 조건이 달라지지 않았다면 다시 묻지 않고 수행하되, 리뷰어 배정·재리뷰 요청·리뷰 댓글·병합은 각각 요청된 경우에만 실행한다.
- 수정 요청이 함께 있으면 수정 후 관련 검증을 수행하고 작업 브랜치를 보고한다.
