# PR Review

작업 중인 저장소의 `AGENTS.md`와 실제 변경 사항을 기준으로 리뷰한다. 스타일 선호보다 사용자 동작에 영향을 주는 문제를 우선한다.

## 검토 대상을 고정한다

- 기존 PR은 현재 base/head와 커밋, 변경 파일, 리뷰 대화를 확인한다. 연결된 GitHub 도구를 우선 사용하고 부족한 기능은 인증된 `gh`로 확인한다.
- 로컬 자체 리뷰는 요청한 기준 브랜치와 커밋 범위를 확인한다. PR 전 리뷰라면 기준과의 커밋 diff뿐 아니라 staged·unstaged·untracked 변경도 범위에 포함했는지 밝힌다.
- 기준을 `develop`으로 고정하지 않는다. 하네스 저장소와 백엔드의 기본 브랜치는 다를 수 있다. 원격을 새로 확인하지 못했으면 로컬 참조 기준이라고 적는다.
- diff 주변의 실제 호출자·보안 필터·SQL·테스트를 좁게 읽는다. 기존 코드와 테스트가 배제한 상황을 새 버그로 주장하지 않는다.

## 변경에 해당하는 항목만 확인한다

| 변경 | 확인할 근거 |
| --- | --- |
| API·인증 | SPEC와 요청/응답 호환성, 게스트 정책, 다른 사용자의 리소스 접근, SecurityConfig·OpenAPI·PUBLIC_ENDPOINTS의 일치 |
| 데이터·쿼리 | 트랜잭션 경계, 중복 처리·동시성, 조회 횟수, 정렬·페이지 경계, 인덱스와 데이터 정합성 |
| Flyway | 버전 중복, 이미 적용된 파일 수정, 빈 DB와 기존 스키마의 업그레이드 경로 |
| 외부 연동 | timeout·실패·부분 성공 처리, 재시도 시 중복 부작용, 테스트와 운영 설정의 차이 |
| 구조·하네스 | 실제 패키지 규칙, 스킬 실행 조건·참조 경로·도구 가용성, 기존 규칙과의 충돌, 설정에 비밀값 포함 여부 |

성능 문제는 쿼리·호출 경로나 측정 근거로 뒷받침한다. 재현 검증이 필요하면 변경에 가까운 테스트를 실행하고 환경 변경이나 라이브 부작용이 필요한 실험은 요청 범위를 확인한다.

## 결과

- 발견 사항마다 중요도, 정확한 파일·줄, 발생 조건, 사용자 영향, 수정 방향을 적는다. 추정만 남은 내용은 확정된 결함과 분리한다.
- 문제가 없으면 그 사실과 검토 범위를 간단히 밝힌다. 빈 리뷰를 채우기 위해 사소한 지적을 만들지 않는다.
- 실행한 테스트, 실행하지 못한 검증, 확인한 CI의 커밋·결과를 구분한다. 로컬 통과를 원격 CI·배포 성공으로 표현하지 않는다.
- 리뷰만 요청받았다면 결과를 현재 대화에 보고한다. 이미 허용된 PR 작성 범위는 수행하되 리뷰어 배정·재리뷰 요청·리뷰 댓글·병합은 각각 요청된 경우에만 실행한다.
- 수정 요청이 함께 있으면 수정 후 관련 검증을 수행하고 작업 브랜치를 보고한다.
