# Spring API Implementation

작업 중인 백엔드 루트의 `AGENTS.md`를 기준으로, 요청한 사용자 흐름을 검토 가능한 크기로 구현한다. 아래 경로는 대상 백엔드 루트 기준이며 실제 위치와 이름을 먼저 확인한다.

## 계약과 구현 위치

1. 요청한 이슈·`docs/SPEC.md`의 관련 부분, 가장 가까운 컨트롤러·서비스·저장 포트·테스트를 읽는다. 문서와 현재 코드가 다르면 차이를 드러내고 요청 범위 안에서 결정한다.
2. endpoint·method, 요청/응답, 오류, 로그인·게스트·리소스 소유권, 기존 클라이언트 호환성을 정리한다. 계약이나 데이터에 영향을 주는 미해결 요구만 질문하고 독립적인 조사는 계속한다.
3. `build.gradle`에서 실제 버전과 포크를 확인한다. 라이브러리 사용법이 불확실할 때만 연결된 Context7 또는 공식 원문으로 해당 버전을 확인한다. Context7 연결이 구현의 필수 조건은 아니다.

## 변경을 연결하는 순서

- 기능의 기존 `domain/service/infra/controller` 구조와 명명법을 따라 도메인 불변식, 서비스 유스케이스, 저장·외부 연동, HTTP 변환을 연결한다. 계층별 클래스 생성을 의무화하지 않고 필요한 부분만 변경한다.
- 데이터 구조가 바뀌면 기존 Flyway 이력과 데이터 영향을 확인하고 순방향 마이그레이션을 추가한다. 요청 범위 밖 리팩터링이나 미들웨어 도입을 섞지 않는다.
- 인증·공개 범위가 바뀌면 `SecurityConfig`, `ArchitectureTest.PUBLIC_ENDPOINTS`, 컨트롤러 보안 문서와 권한 테스트를 같이 확인한다. 공개 경로 허용과 인증된 사용자의 소유권 검사는 별개로 검증한다.
- `AGENTS.md`의 API 문서 규칙에 따라 `@Tag`, DTO의 `@Schema`, 필요한 `@SecurityRequirement`를 반영한다. 문서 UI들이 공유하는 OpenAPI와 관련 SPEC 계약을 맞춘다.

## 검증과 보고

- 도메인·서비스 규칙은 가까운 단위 테스트로, HTTP·DB·S3 경계는 기존 통합 테스트 구성으로 검증한다. 통합 환경 작업이 필요하면 같은 저장소의 `integration-test` 스킬을 읽는다.
- Java 변경은 컴파일과 관련 테스트, 패키지·인증·문서 규칙 변경은 관련 아키텍처 테스트를 확인한다. 통과한 검증은 새 변경이나 실패 근거가 없으면 반복하지 않는다.
- 결과에는 바뀐 API 동작, 중요한 파일, 정확한 검증 범위와 미검증 항목, 작업 브랜치를 적는다. 커밋·푸시·PR 등 외부 작업은 현재 요청에서 허용한 범위로 수행한다.
